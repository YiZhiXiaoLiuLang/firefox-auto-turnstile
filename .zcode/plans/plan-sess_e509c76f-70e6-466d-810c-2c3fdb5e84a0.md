# firefox-auto-turnstile 实施计划

干净浏览器代过 Turnstile → Token 回填给高风险浏览器。单容器方案：基于 `jlesage/firefox`（Alpine 3.24，自带 Xvnc/noVNC/xdotool），容器内跑 mitmproxy + API 服务，GitHub Actions 公开仓库原生 arm64+amd64 双架构构建，推 ghcr.io。

## 架构与数据流

```
调用方(高风险浏览器侧)                容器内                              外部
─────────────────────    ─────────────────────────────────    ──────
POST :8081/solve ───────▶ API 服务(python3 标准库)
  {url, sitekey, timeout}   ├─ 写任务文件 /config/relay/task.json
                           ├─ xdotool 驱动 Firefox 打开 url ──▶ Firefox(窗口)
                           └─ 长轮询 result.json
                                 Firefox ── 代理策略(127.0.0.1:8080) ──▶ mitmproxy
                                   ├─ 目标站文档请求 → 拦截，返回注入页(地址栏仍是真实域名)
                                   ├─ /.relay-token/?t=... → 捕获 token 写 result.json
                                   └─ 其他流量正常转发
                                 Firefox ── Passthrough 直连 ──▶ challenges.cloudflare.com
                                   (api.js 在注入页渲染，用户经 noVNC :5800 点击)
返回 token ←────────────── API 返回 {ok, token, task_id, elapsed}
调用方把 token 填入 cf-turnstile-response 隐藏域并提交
```

**关键事实（已核实）**：jlesage/firefox 底座 Alpine 3.24，Firefox 装在 `/usr/lib/firefox`；Alpine community 源直接提供 mitmproxy 11.0（`apk add mitmproxy`）；策略文件放 `<安装目录>/distribution/policies.json`；`Certificates.Install`、`Proxy`（键名 `HTTPProxy`/`SSLProxy`，端口拼在主机名后 `127.0.0.1:8080`）、`Passthrough` 均支持 Linux；自定义后台服务用 `/etc/services.d/<name>/run` + 空 `respawn` 文件（v4 起不再用 s6-overlay）；镜像自带 xdotool。

**两个关键设计决策**：
1. **challenges.cloudflare.com 走 Firefox 直连（Proxy 策略的 Passthrough），完全不经过 mitmproxy**。原因：若 Turnstile 流量被 MITM，Cloudflare 看到的是 mitmproxy 的 Python TLS 指纹而非 Firefox 真实指纹，会显著提高验证难度甚至失败。目标站点文档必须经 MITM（为了替换页面），但验证流量绝不能碰。
2. **CA 每容器独立生成，不烘进镜像**。镜像公开在 ghcr，若 CA 烘进镜像则任何人可对全部部署签发任意域名证书。CA 在容器首次初始化时生成到持久卷 `/config/mitmproxy/`，policies.json 引用固定绝对路径。

## 核心组件细节

### 1. policies.json（锁定，防用户误改）
```json
{"policies": {
  "Certificates": {"Install": ["/config/mitmproxy/mitmproxy-ca-cert.pem"]},
  "Proxy": {"Mode": "manual", "Locked": true,
    "HTTPProxy": "127.0.0.1:8080", "SSLProxy": "127.0.0.1:8080",
    "UseHTTPProxyForAllProtocols": true,
    "Passthrough": "challenges.cloudflare.com, <local>"},
  "DisableTelemetry": true
}}
```

### 2. mitm 服务（/etc/services.d/mitm/run）
```sh
#!/bin/sh
exec mitmdump --listen-host 127.0.0.1 --listen-port 8080 \
  --set confdir=/config/mitmproxy --set connection_strategy=lazy \
  -s /opt/turnstile-relay/relay_addon.py
```

### 3. relay_addon.py 逻辑（~150 行）
- 按请求懒加载+缓存 `/config/relay/task.json`（mtime 判断，TTL 6 分钟——token 有效期 5 分钟）。
- `request` hook 两条拦截路径（host 均须等于任务 hostname）：
  - 文档请求（path 精确匹配任务 path，忽略 query）→ 直接返回注入页 HTML：加载 `https://challenges.cloudflare.com/turnstile/v0/api.js`，显式 `turnstile.render('#c', {sitekey, callback})`；callback 里 `fetch('/.relay-token/?t=' + encodeURIComponent(token))`（同源请求，无 CORS 问题），成功后页面显示"✓ Token 已捕获"；另挂 `error-callback`/`expired-callback` 显示状态。
  - `/.relay-token/` 路径 → 取出 `t` 参数写 `result.json`，回 200，删任务文件（单次）。
- 其余请求一律正常转发，不碰。

### 4. api_server.py 逻辑（~200 行，ThreadingHTTPServer，监听 0.0.0.0:8081）
- `POST /solve` `{url, sitekey, timeout≤300 默认180}`：校验 url 为 https、无未过期任务（否则 409 busy）→ 写 task.json → 起子进程跑 `nav.sh`（`xdotool search --onlyvisible --class firefox windowactivate --sync` → `ctrl+l` → `type --delay 40 <url>` → `Return`）→ 每 200ms 轮询 result.json 直到超时（504）或拿到 token（200 返回 `{ok, token, task_id, hostname, elapsed}`）。
- `GET /status`（当前任务）、`GET /healthz`。
- 单任务并发模型（浏览器只有一个窗口），全局锁。
- 以 `su-exec ${USER_ID:-1000}` 运行（与 Firefox 同 uid，xdotool 才能连上 X server；`su-exec` 需在 Dockerfile 补装）。

### 5. 容器初始化（/etc/cont-init.d/99-relay-init）
`mkdir -p /config/mitmproxy /config/relay`；若 CA 不存在则用 mitmproxy 的 Python API 生成：`certs.CertStore.from_store("/config/mitmproxy", "mitmproxy", 2048)`（若 API 签名不匹配，回退方案：`timeout 3 mitmdump --set confdir=...` 让其自动生成）。CA 证书 chmod 644、私钥 chmod 600。

### 6. Dockerfile
```dockerfile
ARG FIREFOX_IMAGE=jlesage/firefox:<实现时查 Docker Hub 最新稳定 tag 并固定>
FROM ${FIREFOX_IMAGE}
RUN apk add --no-cache mitmproxy su-exec
COPY src/relay_addon.py src/api_server.py src/nav.sh /opt/turnstile-relay/
COPY rootfs/ /
RUN chmod +x /etc/services.d/mitm/run /etc/services.d/api/run /etc/cont-init.d/99-relay-init /opt/turnstile-relay/nav.sh
EXPOSE 8081
```
（5800/5900 基础镜像已 EXPOSE）

## CI/CD：.github/workflows/docker-build.yml

- 触发：push 到 main、tag `v*`、PR（仅构建不推送）、手动 dispatch。
- `permissions: packages: write`，`GITHUB_TOKEN` 认证 ghcr.io，镜像名 `ghcr.io/${{ github.repository }}`（README 注明仓库需小写）。
- **build job（matrix 原生构建，无 QEMU）**：`linux/amd64 → ubuntu-latest`、`linux/arm64 → ubuntu-24.04-arm`（公开仓库免费原生 arm64 runner）。每架构 buildx `push-by-digest` 推 ghcr，附带冒烟测试 `docker run <digest> --entrypoint sh -c 'mitmdump --version && python3 -c "import mitmproxy" && /usr/bin/firefox --version'`，digest 写入 artifact。
- **merge job**：下载两份 digest artifact，`docker buildx imagetools create` 合成多架构 manifest，打 tag：分支名、`sha-xxxxxxx`、semver（v1.2.3→1.2.3/1.2/latest）、默认分支加 `latest`。
- 缓存 `cache-from/to: type=gha` 按 arch 分 scope。
- PR 时单架构本地构建 + 冒烟，不推送。

## 验证方案（分两级）

1. **全自动冒烟（无需人工点击）**：用 Cloudflare 官方测试 sitekey `1x00000000000000000000BB`（invisible、自动通过、不校验域名）+ 任意 https URL（如 `https://example.com/login`，反正文档会被 MITM 替换），整条链路 API→xdotool→MITM 注入→渲染→回调→捕获→返回全部自动完成，返回 dummy token `XXXX.DUMMY.TOKEN.XXXX` 即链路通。
2. **人工交互验证**：测试 sitekey `3x00000000000000000000FF`（强制交互挑战），经 `http://localhost:5800` noVNC 手动点击，验证真实交互路径。
3. 本机有 Docker 则本地 `docker compose up` 跑上述两级；无 Docker（本机为 Windows，前面检查被计划模式拦截，实现阶段再确认）则 git init + 推 GitHub 由 CI 验证，按 CI 日志迭代。

## 已知限制与风险（写入 README）

- 部署 IP 的信誉影响 Turnstile 难度，建议部署在干净网络；challenges.cloudflare.com 已直连保证 TLS 指纹干净。
- token 5 分钟有效、单次使用，API 返回后需尽快提交；高风险浏览器侧需自建 `input[name="cf-turnstile-response"]` 隐藏域回填（examples/fill-token.js 给示例）。
- v1 单任务串行、验证需人工点击；自动点击（xdotool 坐标）、并发、pre-clearance 模式均列为后期。
- noVNC(5800) 有公网暴露风险，README 强调用 VNC_PASSWORD/防火墙/仅内网访问；mitmproxy 仅监听容器内 127.0.0.1，不会对外。
